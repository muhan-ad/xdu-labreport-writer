### F01：审核状态的“CAS”保护仍然无效

- **位置：** [core/states.py:41](E:/agent-project/labreport-writer-manager/core/states.py:41)。
- **原因：** 写入前增加了一次读取版本比较，但最终仍是不带原子条件的 `put_json`。两个任务可以一起读到旧版本、一起通过复查，再依次覆盖。
- **复现结果：** 两个线程写入不同审核条目，都没有报错，最终只保留 **1 条**，预期 **2 条**。
- **影响：** 多人审核或后台任务同时更新时，可能丢失状态与操作记录。函数名 `_write_cas` 和重试次数不能提供真正的互斥保证。
- [ ] **修复建议：** 使用支持原子版本条件/事务的状态存储，或统一由一个串行服务写入；不能只增加一次读取。补充真正同时写入的竞争测试。

### F02：发布锁没有保护完整发布过程

- **位置：** [云端锁](E:/agent-project/labreport-writer-manager/core/package.py:94)、[发布流程](E:/agent-project/labreport-writer-manager/core/package.py:319)。
- **问题 A：** 读取当前版本、计算新版本、构建固定文件名 ZIP、计算摘要都在取得本机锁之前完成。即使最终提示“已有发布任务”，另一个任务也已经可能覆盖 ZIP。
- **复现 A：** 预先占用 `PUBLISH_LOCK` 后调用发布，虽然最后抛出 `PublishBusy`，`data-package-1.0.2.zip` 仍已生成。
- **问题 B：** 云端锁采用“读取锁 → 普通写锁”，没有原子抢占。两个客户端同时看到空锁即可同时成功。
- **复现 B：** 两个不同 owner 同时申请假 COS 锁，**两者均成功返回**。
- **影响：** 同版本竞争、包与摘要不一致；互斥前的源码合入/失败回滚也未被完整保护。
- [ ] **修复建议：** 锁覆盖版本读取、源码候选处理、打包与发布的整个过程；每次任务使用独立临时路径。跨机器采用真正原子的互斥方式，并在锁内重新读取版本。

### F03：禁止重定向的配置没有作用于实际请求

- **位置：** [core/netguard.py:19](E:/agent-project/labreport-writer-manager/core/netguard.py:19)、[MinerU 客户端](E:/agent-project/labreport-writer-manager/core/mineru.py:65)。
- **原因：** `requests.sessions.Session.max_redirects = 0` 修改的是类属性；创建 Session 时，实例自身仍初始化 `max_redirects=30`，覆盖类属性。
- **复现结果：** 导入项目 netguard 后，类属性为 **0**，实际 `requests.Session().max_redirects` 为 **30**。
- **影响：** 部分调用显式设置了 `allow_redirects=False`，这些调用有效；其余上传、轮询、ZIP 下载不能依赖这段“全局关闭”代码。检查过的 URL 仍可能被重定向到其他地址。
- [ ] **修复建议：** 每个相关请求显式禁止重定向，或统一使用经过配置的 Session；确需重定向时逐跳校验。删除误导性的全局类属性补丁及注释。未对内网发起利用测试。

### F04：管理端写请求错误处理存在不可达分支

- **位置：** [main.js:156](E:/agent-project/labreport-writer-manager/main.js:156)。
- **原因：** POST 等写请求现在只循环一次，`attempt` 只有 0；catch 内却仍然只在 `attempt === 1` 时返回错误对象。
- **复现结果：** 模拟 POST 网络失败，真实处理器返回 **`undefined`**，而非 `{ok:false,error:...}`。
- **影响：** 调用界面可能显示泛化错误，或在读取 `r.ok` 时再次出错，表现为点击无响应/原因不清。限制写操作重试是正确方向，但旧返回条件没有同步修改。
- [ ] **修复建议：** 最后一次尝试始终返回结构化错误；为成功、HTTP 错误、网络异常和无效 JSON 都定义一致返回结构。

### F05：同步只检查文件存在，不检查是否完整

- **位置：** [core/sync.py:103](E:/agent-project/labreport-writer-manager/core/sync.py:103)。
- **原因：** 下载直接写最终路径；失败只记录警告。后续遇到 `dest.is_file()` 就跳过，没有校验大小、摘要或完成状态。
- **复现结果：** 假下载器写入 `partial` 后抛错；连续同步两次，下载只调用 **1 次**，残片仍在。
- **影响：** 晚到附件补下载功能已经补上，但网络中断留下的损坏文件依然可能长期不能自动恢复。
- [ ] **修复建议：** 下载到临时文件，校验成功后原子改名；失败删除临时文件；本地记录大小/摘要，发现损坏时重新下载。

### F06：识图服务地址输入会被旧值覆盖

- **位置：** [updateVisionFields](E:/agent-project/labreport-writer/src/ocr.js:38)、[设置面板展开](E:/agent-project/labreport-writer/src/renderer.js:2223)。
- **触发：** 独立识图服务已有旧地址，输入新地址但尚未保存；收起并重新展开识图配置面板，或触发相关服务切换。
- **原因：** 展开会调用 `updateVisionFields()`，其独立模式直接把输入框重置为 `dataset.ownValue` 或已保存地址；输入时没有对应更新备份值。
- **复现结果：** 输入框为 `https://new.example/v1`，备份为旧地址，调用后输入框变回 `https://old.example/v1`。
- **影响：** 用户以为设置过的新地址被悄悄撤销，后续可能保存旧值、绑定错误服务或误认为配置没有生效。
- [ ] **修复建议：** 面板展开只控制显示；仅在实际切换继承/独立模式时转换地址状态，并保存当前未提交输入。

### F07：增量更新仍然缺少基线保证

- **位置：** [build_zip](E:/agent-project/labreport-writer-manager/core/package.py:123)、[管理端推送入口](E:/agent-project/labreport-writer-manager/ui/app.js:571)。
- **已改善：** 增量包现在自动包含 common，解决了遗漏公共库的部分问题。
- **仍存在：** 最新清单仍只指向一次增量包，没有声明客户端必须具备的基线，也没有补丁链或自动全量兜底。
- **例子：** 1.0.2 更新甲、1.0.3 更新乙；1.0.1 用户直接更新到 1.0.3，仍漏掉甲，却被标记为最新。
- [ ] **修复建议：** 小项目优先让最新清单指向完整快照。提示“定期发布全量”只能降低发生概率，不能保证正确性。

### F08：旧数据包原地址保留时间不足

- **位置：** [core/package.py:384](E:/agent-project/labreport-writer-manager/core/package.py:384)。
- **已改善：** 新包上传失败时，旧包现在不会提前被移走。
- **仍存在：** 新清单发布成功后立即移动旧 ZIP。已取得旧清单但尚未完成下载的客户端仍会请求旧地址，从而失败。
- [ ] **修复建议：** 发布包使用不可变地址，旧地址延迟清理；按保留窗口或最近若干版本处理，不要在切换后立即删除原地址。

### F09：最终校验只覆盖了部分合入入口

- **位置：** [manager.py:160](E:/agent-project/labreport-writer-manager/manager.py:160)、[界面后端校验函数](E:/agent-project/labreport-writer-manager/backend/server.py:295)。
- **原因：** 界面后端已加入 `validate_candidate_for()`；命令行 `cmd_merge()` 仍直接读取候选 JSON 并调用 `merge_candidate()`。底层合并仅检查章节/文本形状和去重，不执行完整内容规则。
- **影响：** 手动使用 CLI 时，不合格占位符、内容规范问题等仍可被合入。单独存在 `validate` 命令，不等于 `merge` 强制验证。
- [ ] **修复建议：** 把必须执行的最终校验放到两条入口共用的业务层；GUI、CLI 和其他调用者都不能绕过。

### F10：IPC 来源验证范围过宽

- **位置：** [main.js:110](E:/agent-project/labreport-writer-manager/main.js:110)。
- **原因：** `fromApp()` 仅判断顶层框架且 URL 以 `file://` 开头，没有核对指定 `ui/index.html` 和当前窗口身份；窗口也未形成完整导航限制。
- **影响边界：** 普通互联网网页不会直接通过该判断，但如果应用顶层导航到其他本地 HTML，该页面可能被当作可信应用来源。不是已验证的远程任意执行漏洞。
- [ ] **修复建议：** 精确匹配应用 URL、当前 webContents 和主框架，拒绝非预期导航与新窗口。不要把“本地文件”直接等同于“本应用页面”。
